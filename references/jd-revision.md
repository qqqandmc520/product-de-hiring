# 模式四：岗位JD修订

## 输入边界

按 `intake.md` 区分修订与新写。已有JD或足够的岗位背景即可开始；候选人简历不是必需。缺招聘反馈可优化JD结构与表达，但不能称为从面试归因；缺旧稿可以起草，不能虚构原表述对照。

## 先归因，不先加要求

读取现行JD和岗位画像、面试原材料、实际覆盖及结论，按证据区分以下情况。样本少时只形成可验证的改进假设，不能据两名候选人推断人才市场普遍如何。

| 发现 | 可能原因 | 对应处理 |
| --- | --- | --- |
| 候选人长期未亲自做产品判断，但JD只突出统筹 | 产品本体责任和亲自参与程度未写清 | 写明关键取舍、端到端体验、作品走查与上线后修正责任 |
| 候选人有增长数字，但不能解释产品改动 | 筛选证据要求过泛，或归因尚未核实 | 要求具体案例/指标口径/个人贡献；保留增长职责 |
| 某能力没有评估材料 | 可能是没问、没看作品或纪要不足 | 改面试与材料准备，不先据此加JD硬门槛 |
| 两位候选人在同题暴露同一关键缺口 | 可能是岗位要求不明，也可能是题目诱导或样本偶然 | 回看中性追问与任务条件，提出下一轮验证，不能直接泛化 |
| 行业经历匹配但产品判断证据薄 | 行业经历被当成能力替代 | 把必需能力写成可观察行为，领域经验按真实必要性分必需/加分 |
| 产品能力强但业务职责不足 | 岗位组合需要澄清 | 继续分别验证，讨论职责范围与资源，不能擅自删除用户目标 |

## 修订办法

先写“为什么改”：证据位置、岗位影响、现有表述缺口、替代解释。只调整有依据的内容，不以招聘更容易为由把产品负责人改为体验负责人，也不默认所有部门都需要增长、AI或旅行经历。

再写修改对照：**原表述 → 建议表述 → 证据依据/应用推演 → 对筛选和面试有什么变化**。明确属于保留、澄清、调整必需/加分或新增验证，不能伪装为模型原文要求。

可发布文本通常保留四部分：岗位目标、主要职责、必需能力、加分经验。把P1–P7转化为与岗位任务相关的自然表述，不把内部术语和整张评分表塞入对外JD。

例如写“能围绕用户完整任务，明确关键规则与边界，组织信息与操作，处理等待、中断和结果确认，并推动体验验收与持续改进”。是否强调某些任务由岗位画像决定，避免把所有子项写成无限长理想型。

岗位责任与结果仍须具体。例如原岗位对DAU负责，修订后依然说明增长责任、协作资源、指标及产品改动的关联；产品DE模型聚焦产品本体不构成删掉DAU的理由。

## 交付与验证

交付四项，可合并成一份文档：

1. 问题归因及证据，区分已观察问题、问法问题和待验证假设。
2. JD修改对照和理由。
3. 可直接审阅的完整JD建议稿，不含真实候选人姓名、面试引用、内部评价和未授权公开的业务数据。
4. 下一轮筛选与面试如何相应调整：关键案例要求、必问题、补证方式和观察标准；更新岗位画像版本并说明生效范围。

默认只是建议稿，不自动发布。推广前建议由岗位负责人、面试官共同用下一轮材料校准：是否吸引到更相关的经历、是否能找到需要的产品判断证据、是否仍出现把未观察当不足。设定复盘窗口和样本量由部门工作节奏决定，不承诺小样本可证明因果。
