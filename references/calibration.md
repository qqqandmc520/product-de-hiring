# 跨部门校准与虚构练习

以下均为招聘应用建议和虚构材料，不是能力模型正式案例，也不是真实候选人。

## 推广方式

先选择一到两个有实际招聘需求的部门试用，各自确定岗位画像。用同一份已授权脱敏的简历、纪要和作品，至少两位评估者先独立记录证据与状态，再对齐。若只有一位评估者，先自检，不能宣称评估者间一致。

记录分歧：能力归属、观察状态、证据引用、岗位要求或最终建议。对齐不是强迫结论相同，而是让相同事实使用相同定义、避免漏证与误判；对于真实取舍保留异议和补证方案。

建议同时看：来源定位是否可复查；未观察项被误判比例；同一关键证据被不同理解的原因；关键岗位要求是否漏评；去留建议分歧能否由补证解释。样本量与观察窗口预先约定，不把某个一致率设为本技能强制通过线。

模型版本、技能版本、岗位画像版本分别管理。新JD和标准只对约定轮次生效；已评候选人若需要重新比较，显式重评并保留原记录。技能变更应由具体失败案例支持，再用正反案例复查。

## 四环节的通用校准方法

校准材料由试用部门从本次真实岗位选取已授权脱敏材料；没有材料可先检查模板和引用，但不能自造一个产品方向后宣称适合所有部门。

1. **岗位与筛选**：各评估者先独立提炼使用方明确的用户任务、责任边界和要求分层，核对是否凭模板添加了行业、技术、指标或管理条件。再从同一履历提取线索，不用候选人的强项倒推招聘需求。
2. **面试**：从该岗位生成同一基线场景及观察任务，保持最低表现和必要专业事实一致。检查是否存在只在标题强调核心、实际只浅问，或因为通用时间表而硬塞未要求的独立职责。
3. **面后**：比较证据位置、实际机会、提示程度、状态和岗位影响。一个已观察缺口不扩张成七项都弱；未知不计作不足。去留依据回到预先明确的要求，不凭状态数目裁决。
4. **JD修订**：先区分要求不清、问题机会不足与候选人实际不匹配，再同步调整JD及验证任务。不得因某次试用的特殊场景向其他岗位添加门槛。

### 无行业设定的虚构证据片段

以下只用于校准证据状态，不是预置岗位画像或面试题。是否与实际岗位相关、是否构成核心要求均须由本次使用方需求决定。

- 12:10，候选人说明同一任务中的对象身份与变化规则。这是现场推演，只支持其具体判断范围，未证实实际落地。
- 18:20，面试官给出完整解决办法后，候选人仅回答“对”。这不能作为其独立发现和解决问题的证据。
- 21:00，题中事实明确“一部分完成、一部分失败”，经中性澄清后，候选人仍把全部结果描述为完成且未解释矛盾。可记录具体问题及观察机会；是否足以不推进取决于本岗事先明确的最低表现。
- 其余内容未问，也无作品。不据此推断其余能力低；应记录未充分观察和是否需要补证。

不能把上述证据片段里的任务或某项能力设为跨岗位统一重点。具体案例、专业事实和验收任务应从使用方当前画像生成。

## 额外反例

- 仅有业务成果数据：可以是相关职责线索，不能直接支持七项产品能力，也不能将某指标偷换成另一指标。
- 候选人采用不同交互或技术形式：检验相同用户目标、事实边界、控制及恢复条件，不因路径不同直接判错。
- 缺少必要专业事实：允许澄清或明确假设，不鼓励编造专业方案。
- 面试计划覆盖七项而纪要只问三项：按实际材料评三项，其余标未知。
- 新材料补足关键证据：允许结论变化，保留岗位版本与新旧依据，不能维护历史答案。

## v0.4.1通用性人工回验

| 使用方输入 | 应观察的行为 | 失败表现 |
| --- | --- | --- |
| 只有技能名，没有方向或JD | 询问当前环节；引导提供产品、用户任务和岗位责任，不预填方向 | 自动沿用以往试用岗位或原件案例 |
| 背景足够但无正式JD | 依据本次输入形成草案与要求分层，未知标待定 | 强制先上传JD，或擅自补行业/技术/经营指标 |
| 只要求独立产品判断，无管理或经营职责 | 面试时间用于本岗关键任务，不预留固定业务/带队题 | 按默认提纲硬塞独立职责 |
| 当前任务与原件案例不同 | 迁移能力定义，按当前任务生成场景 | 把原件案例当必做产品或标准答案 |
| 换到一个新岗位 | 重新核对方向、用户、责任及层级，不沿用旧门槛 | 将上一岗位的核心要求自动复制过来 |
| 用户提供特定行业、技术或指标要求 | 依据本岗材料明确具体范围、必要性与证据，保持产品/业务边界 | 因强调通用而删掉使用方真实要求 |

这些是人工复测标准，尚未自动证明交互质量或跨部门一致性。

## v0.4要求分层回验

这些是虚构的人工复测情景，不是已经通过的行为测试。可用 `python3 scripts/test_case_tools.py` 检查结构约束，但交互质量、观察深度和真实判断仍须人工跑流程验证。

| 输入/变化 | 应观察的行为 | 失败表现 |
| --- | --- | --- |
| 已明确任务甲，又新增阶段目标乙 | 保留产品核心，澄清新增目标的具体层级；不推断原问题已解决 | 因新增目标删除原要求 |
| “有某类行业或技术经历最好，核心是把用户任务做顺” | 提炼主因，核对这项经历是否加分；用一次取舍澄清歧义 | 将所有重要项都当核心，要求用户给七项权重 |
| 加分为行业经验，跨行业候选人有具体产品案例 | 先看核心可迁移线索，缺加分不拒绝 | 没做过该行业即不推荐 |
| 独立业务职责强，但预定核心产品任务已观察实质缺口 | 保留优点，依据核心最低表现与实际机会解释建议 | 加分或业务成果抵消产品缺口 |
| 简历有核心相关项目，但七项与核心均未充分核实 | 判断是否值得初试，写验证重点 | 必须所有项supported才面试，或称已证实符合岗位 |
| 使用方明确某项为核心，准备60分钟面试 | 有足够展开该任务的本人判断、取舍、验证及结果的机会，且总时长准确 | 仅留4分钟问一个数字，其他时间照抄通用提纲 |
| 可培养为业务规则，现团队有专家但期限未定 | 记录已有支持与待定节点，核对补齐可行性 | 因不会直接拒绝，或因愿学默认已满足 |
| 面后未问核心之一，另一个核心有充分缺口 | 分别记未知与gap，解释独立缺口是否足以影响阶段建议 | 把未知累计成否定，或要求无限补面才敢给建议 |
| 换一位候选人，强项刚好是原加分项 | 标准不变，调整追问而不调整核心层级 | 为候选人临时改画像 |
| 旧记录无要求分层，用户请求接续 | 依据原岗位形成暂定分层并披露，重大歧义才问；历史结论保留 | 假装以前已确认新标准，自动重写历史结论 |

## v0.3交互与领域边界回验

以下是虚构测试输入和观察标准，不是预设所有岗位或候选人的唯一结论。用于实际交互回验，不能仅凭文档含有这些规则宣称测试通过。

| 输入/变化 | 必须观察到的行为 | 失败表现 |
| --- | --- | --- |
| “招个行业专家负责产品”，未说主要判断责任 | 提一个贴合语境的选项问题，区分提供专业方案、亲自决定产品、两者兼任；保留暂定 | 按头衔直接认定产品DE，或先问一长串未确定需要的行业知识 |
| 已说明亲自取舍、走查体验，且明确要筛简历 | 记录产品核心及依据，必要知识按任务另列，直接开始已有材料 | 再选一次岗位类型、等待用户认可每个画像字段 |
| 用户举某个功能为例，随后明确尚无路线 | 一直作为举例/探索，不写成必做功能或硬门槛；不反复追问上线范围 | 将例子写进入职承诺，或每轮重写整份画像 |
| 用户面对开放问题不知如何说 | 给2–4个贴合已有描述的选项，可组合/补充/暂不确定，说明影响哪个招聘标准 | 重复原问题，或用单选强迫舍掉复合职责 |
| 来源领域知识与业务成果强，只转交业务需求 | 分别支持业务证据，产品判断待验证；产品主导岗不被营收补偿 | 直接推荐为已符合产品DE，或反向认定永久不具产品能力 |
| 跨行业产品案例具体，能核实专业事实并完成产品化 | 认可相应产品与转译证据；独立核实入职必需知识能否补齐 | 因没有某类行业经历一票否决，或因产品强而省略硬知识要求 |
| 对必要专业规则模糊，补给统一事实后能做产品判断 | 补事实前的知识表现和补后产品表现分开；若为硬要求保留缺口 | 把缺事实直接记产品gap，或补完后假装原本就懂 |
| 实际职责是制定专业标准，产品由别人负责 | 标业务主导，说明产品模型不认证专业资格；整理可做部分 | 把产品七项低覆盖当作专业能力差 |
| 产品关键缺口证据充分，但独立业务职责表现亮眼 | 明确产品核心当前不支持，业务强项仍保留；给当前阶段受限建议 | 加权平均成通过，或无限补面避免当前判断 |
| 仅问“现在到底推荐吗”，没有新证据 | 同一标准解释当前推荐是验证机会还是岗位匹配；必要时说明决策约束变化 | 随追问口气反转能力结论，且不解释阶段差异 |

实际试用时另记提问轮次、重复问题、用户纠正的例子误读、岗位属性是否可追溯、产品/业务双结论是否可见。不能把固定问答轮数当KPI，关键是信息是否足够且没有无效追问。

## v0.2首次输入引导的情景校准

以下检查任务路由与材料依赖；没有实际候选人结论，不替代独立用户实测。

| 初始输入 | 合理动作 | 应避免的行为 |
| --- | --- | --- |
| 只说“使用技能” | 询问当前环节，介绍JD可由岗位简述替代，之后按需接收材料 | 一次索要JD、全部简历、全部纪要和七项权重 |
| 已给JD＋简历，要筛选 | 直接读材料、建画像草案并筛选 | 重问做哪个环节、要求用户重传、等完整画像确认才开始 |
| 只有简历，问岗位适配但没有岗位信息 | 先提取履历线索，补问岗位依据 | 根据候选人履历自行倒推岗位，再给去留 |
| 没有正式JD，但已清楚说明用户、任务及责任，要准备面试 | 用岗位简述建草案；有候选人依据则做专属提纲，否则做通用提纲 | 把正式JD作为所有输出的必要条件 |
| 岗位依据＋实际面试问答，没有简历 | 评估已观察回答，列明材料范围 | 因缺简历完全拒绝面后评估，或假装有履历佐证 |
| 岗位依据＋一句“感觉不够深” | 补关键原始问答，可先整理评估重点 | 将面试官评价当作已观察缺口 |
| 只有岗位背景，想写JD | 起草JD并说明无旧稿/招聘反馈 | 索要候选人简历，虚构原文对照和面试归因 |
| 已存岗位画像，新增一份简历 | 复用画像，核对文件归属后筛新增人选 | 要求整套重新填写，或未经请求重评全部人选 |
| 材料无法读取或不知归属哪位候选人 | 说明具体缺失或归属问题，补问并继续无依赖工作 | 以未读取的内容作判断，错配证据，因输出格式未选而暂停 |
