# 模式二：面试准备

## 输入边界

按 `intake.md` 复用岗位依据和候选人材料；专属提纲需要其简历、项目介绍或已有记录之一。没有候选人材料可先出岗位通用提纲，不能虚构其经历。未给时长默认60分钟并说明，无须为默认值另设确认。

## 设计原则

继承 `role-boundary.md` 中的岗位属性及必要业务知识范围。产品DE面试的主要时间与关键观察机会用于产品判断和真实用户任务，不被行业知识考试、经营复盘或管理经历挤占；不规定跨岗位统一权重。若用户安排与此冲突，明确当前能观察什么、缺什么。必要业务知识仍需验证，专业裁决题由相应领域评估者负责，不用产品模型代替。

从候选人记录继承线索和未知，围绕一个真实案例持续走查，再用同一岗位场景观察迁移。问题使用日常语言，面试官备注中标能力，不向候选人逐项背诵P1–P7。不要用七道概念题替代一次完整任务，也不要用同一条泛泛回答证明七项。

为每段写清：自然主问、必要时的中性追问、观察什么、何时停止追问、关联能力和记录位置。不要一开始连抛五个问题。问题答案应允许多种合理解法；观察取舍依据、用户结果和失效条件。

按 `role-priorities.md` 继承H:要求及最低表现，先列“本轮要改变哪些核心未知”，再排时间。每段注明对应H:要求、希望新增的证据及最低表现，不能只在开头说有重点、随后照抄平均分配。其他必需保留验证；可培养主要核支持与学习条件，加分仅按辨识价值安排，不挤掉核心观察。候选人间可调整追问，但不降低同岗最低表现、临时加门槛或改变专业事实基线。

## 60分钟起点示例（须按核心未知重排）

| 时间 | 内容 | 目标 |
| --- | --- | --- |
| 0–4分钟 | 对齐本人责任、选择一个具体项目 | 确定用户、范围、个人贡献 |
| 4–24分钟 | 真实案例深挖与作品走查 | 20分钟，覆盖七项的具体入口，优先岗位关键项 |
| 24–40分钟 | 岗位场景推演 | 16分钟，看判断迁移及关键未知 |
| 40–50分钟 | 岗位关键未知补证 | 10分钟，按本岗要求选择；只有明确存在独立职责时才用来验证该职责 |
| 50–56分钟 | 未覆盖关键项补证 | 6分钟，按前段实时缺口选择，不机械问完题库 |
| 56–60分钟 | 候选人提问与结束 | 4分钟 |

实际计划的时间合计应为用户约定时长。每项注明主要观察段和备选入口；一小时仍无法深入的项目标明后续作品走查/二面，不能许诺一小时充分验证全部能力。实际覆盖由纪要决定，不由计划决定。

上表不是固定题单或统一比例，不预留特定业务或管理考题。每条核心要求都须有足够展开“任务—本人判断—取舍—验证—结果/局限”的观察机会，不能只留一个浅问。可把真实案例中的一部分时间深入该要求，也可按关键未知重排；同一时段不因关联多项要求而重复计时。独立职责只有本岗明确需要才安排，记R项，不能冒充产品P项；本岗未要求的职责不自动插入。已有充分证据的项可以少问，把时间用于关键未知。

交付前检查：每条核心要求有可执行观察任务和足够展开/追问的机会，或明确前轮依据/后轮安排；不是简单在所有段落贴上全部P/H标签。时间不够时先删低优先级问题或安排后续，不压成七项各问一句。

## 真实案例的自然主线

起问：“挑一个与你应聘职责相关、你亲自做过关键判断的项目。用户当时要完成什么？最难的一次取舍是什么？”是否追问上线结果、试点验证或方案判断，依本岗要求与实际项目阶段决定。

候选人没有已上线案例时，可以讲试点/规划，但分开观察方案质量和结果证据，不强迫其编造落地。

| 追问入口 | 自然设问示例 | 观察重点 |
| --- | --- | --- |
| 关键判断 | “当时有哪两种都说得通的做法？你为什么选这个？什么情况会改主意？” | P1价值、边界、规则、取舍；个人决定与团队贡献 |
| 领域约束 | “碰到业务规则说不清或互相冲突时，你怎么弄清楚？最后产品里怎么体现？” | P1转译；专业事实不编造，硬约束与偏好有区别 |
| 判断责任 | “这条专业规则是谁判断的？你亲自决定了哪些产品做法？把其中一次争议从专业结论到用户实际使用走一遍。” | 区分来源领域判断、产品独立贡献与协同执行；只转述需求不是充分产品证据 |
| 用户起点 | “用户第一次到这里，通常已经知道什么，还会拿不准什么？你怎么发现的？” | P2真实预期、认知负担、自主选择 |
| 文字 | “看一下当时这个名称/状态。用户会怎么理解？如果请你现在改一句，你会怎么写，为什么？” | P3具体意义、一致性、行动条件；不用口才代替 |
| 结构 | “任务做到一半，用户怎么找到相关内容、知道自己在哪，再回到原来的地方？” | P4分类、层级、定位和回路 |
| 行为闭环 | “沿着用户的一次操作走一遍。哪里算已经生效？如果不是他想要的结果，怎么处理？” | P5意图、响应、确认及纠错；不暗示必须加确认框 |
| 时间过程 | “要等一阵、离开再回来，或者只完成一部分时，用户看到的进展和下一步是什么？” | P6连续性、中断、异步与恢复；不只工程速度 |
| 感知验收 | “给我看一处你要求改过的画面。哪里先被看见、哪里不该抢注意？你怎么验收，在哪种环境容易出问题？” | P7感知层级、强度、品质、真实环境；不要求独立制图 |
| 结果回看 | “上线后哪些变化支持了你的判断？有没有相反结果，或者后来发现做错的地方？” | 产品效果、因果归属、复盘；业务指标另核 |

按回答选择追问，先让候选人独立展开。答得抽象时请其举一个实际界面/对象/状态；必要时澄清用户和目标，不代给解决方案再让其赞同。

## 岗位场景的构建与使用

用画像中真实的用户任务设置简短事实卡：用户目标、当前状态、已有信息、资源/领域约束、一个冲突或变化；标明可由候选人澄清的未知。不要求其背诵行业事实。

自然起问：“如果明天你接手这个问题，你会先弄清什么？我们可以先围绕一位具体用户，把他从开始到完成走一遍。”

统一基线事实和核心观察点，允许各候选人不同路径。同轮不要只对某个人增加难度。变化条件按预先计划或回答需要中性引入，如任务中途改变目标、结果部分可用、用户回来继续；记录引入时点和是否已给关键提示。

场景目标不是面试官心中的唯一页面。候选人选自动执行、模型推断或自由对话时，继续问“你依赖什么条件？用户如何知道发生了什么？条件不成立时怎么办？”同样检验确定流程，不预设一种实现更高级。

为区分行业知识与产品判断，可先让候选人指出需要核实的事实，再提供同一份已确定的专业规则，观察他如何转成产品对象、约束、解释、操作及异常处理。记录补充的事实与提示，不能先给产品解法再当自主表现。若岗位确需已有行业知识，单独记录补事实前的表现和必要性，不以补事实后的产品表现抹去真实知识缺口。

观察表与“可能的好表现/风险”留在面试官备注，不当作暗示读给候选人。候选人合理指出信息不足时，补充统一事实或允许明确假设后继续推演。

## 使用方明确的独立职责

先核对画像中是否真的存在产品本体之外的职责，再用该职责的任务与成功标准生成问题。没有明确要求时，继续产品任务走查，不补一段通用业务或管理考试。

可用的中性问法：“针对岗位里这条职责，选一次你亲自承担的任务。目标和边界是什么？你决定了什么，结果怎样，有什么能支持你的解释？”随后按本岗定制追问，不照搬其他岗位的指标或经历。

涉及指标时核定义、基线、周期与本人贡献，不同指标不能相互替代；涉及专业裁决时由相应领域评估者判断。是否带人、负责经营或跨团队交付均由使用方明确，不从“专家”或“负责人”头衔自动推定。

## 交付形态

形成可直接使用的计时提纲和覆盖表，含：时间段、主问、2–3个按需追问、H:要求及层级、最低表现、关联能力、证据记录栏、停止条件。附场景事实卡、未覆盖项、已有材料和作品准备建议。七项覆盖与要求优先级分别可见，不要求所有题都问完。候选人前置准备量应与岗位及阶段相称；避免索取未公开公司资料。
