# 模式一：简历筛选

## 决策范围与输入

默认回答“依据当前简历，是否值得安排本岗位初试”，不认证最终胜任，也不代替排期。已有岗位依据和可读简历就开始，不为确认此默认范围增加一轮询问；用户指定其他范围时遵从并记录。

将三件事分开：简历适配建议、推荐优先级、实际招聘进度。已面过、待排期等只记流程备注，不改变简历建议或混入推荐人数统计。用户要求安排面试时再结合进度决定实际动作，不重复安排已完成的轮次。只有文件名与简历姓名不同，能明确识别同一份材料时保留两者和稳定候选人ID，不作为能力门槛；多份材料归属冲突会混淆证据时才澄清。

输入缺失按 `intake.md` 引导。岗位依据不强制是正式JD；没有岗位背景时先提取履历线索，不直接给岗位去留。历史筛选表先核版本，不继承答案；本轮只评简历时不把既有面后结论混入依据。只问会改变当前建议的岗位歧义，其余未知显式保留。

沿用 `role-priorities.md` 中同版H:要求：先核心，再其他必需，最后可培养与加分。未分层时从当前岗位信息提炼；不从候选人强项倒推标准。入职或录用必需不等于简历必须充分证明；只有使用方明确的初筛条件才作为该阶段条件，不把全部要求自动前置。

## 怎样提取和解释线索

阅读完整材料，提取个人负责范围、用户任务、本人判断与取舍、落地状态和结果。头衔、公司、工具名和指标数值本身不证明产品判断。简历自述保持未独立核实；指标保留名称、分母、基期、周期及归因缺失，不同指标不能互换。岗位未要求的行业、技术、管理或经营条件不额外增加。

每条决定性线索写出：**原页码 → 本人做了什么 → 对应哪条要求 → 为什么相关 → 最多支持到哪里**。按 `evidence-policy.md` 逐条解释直接相关或可迁移的依据，不按共同P/R标签自动挂接所有证据，也不将“没有相关证据”包装成弱支持。同一案例可支持多项，但每项分别说明，不重复计算案例或优势；必需与加分有重叠时说明加分多出的价值。

先看可迁移的任务复杂度、责任及判断，再看行业和工具匹配。一般产品经验不自动证明本岗具体业务知识，业务成果也不自动证明产品能力。简历中的规划、参与和独立落地分别记录；成熟度须有当前岗位定义的判断及落地线索，不能由术语推定。

## 核心支持是否足以邀请

先判断本次招聘主因是否获得实质支持，再考虑尚未核实的深度。**没有写出不等于不会，也不等于值得本岗位初试。** 缺乏足够核心线索可给暂不建议，不必等到证明其能力有缺口；材料可读但核心支持不足不归为暂无法判断。

对以用户任务和体验改善为主因的岗位，从完整履历找出可定位的用户任务/问题，以及本人实质产品判断或改变。说明它帮助用户理解什么、作出什么决定或完成什么目标；若材料未写，保留未知，不替候选人补因果。具体任务与改变已清楚，原因依据、验收或结果尚待核实，可以进入初试；只有“提升体验”“全链路优化”或零散功能名，不能等同于已有核心判断。

区分每条线索的支持对象与上限，不给人贴永久类别：

| 材料主要证明什么 | 怎样使用 |
| --- | --- |
| 获客、渠道、补贴、激励、触达或经营结果 | 按实际支持相应职责；非投流也不自动等于产品力增长 |
| 局部表达、入口、标签、承接或转化改造 | 保留对应产品能力线索；核用户目标、改变和本人贡献，不自动证明完整体验或负责人范围 |
| 针对具体用户任务改变规则、组织、行为或持续过程 | 解释对应核心要求及迁移边界；结果未独立核实不抹掉具体线索 |
| 围绕核心任务持续取舍、迭代或演进 | 结合承担范围，判断是否支持本岗独立负责的要求；项目规模和头衔不替代实质 |

同一案例可同时有增长与体验贡献，分别解释。增长背景不排除真实产品判断，局部工作也不天然低价值；能否支持本次邀请取决于目标职责。若招聘完整产品/核心业务负责人，不以一处浅层优化代替相应责任范围；也不要求必须做过整款产品或任过同名头衔。

推荐必须说清：**哪条具体核心依据已成立到值得验证的程度、尚缺什么、为什么可以留到面试**。不能只有“其他优点很多，体验待验证”。相关线索不等于充分邀请依据；核心支持明显不足时，行业、技术、增长、管理及案例数量都不补偿。核心未充分证实时不机械拒绝，须解释已有材料对本次主因的实质支持，不要求所有核心或七项均充分证实。

## 初试建议的门槛

| 建议 | 适用依据 | 应说明什么 |
| --- | --- | --- |
| 建议初试 `invite` | 本次招聘主因已有足够具体的个人产品判断/改变线索，支持范围与目标职责相称或有实质迁移理由；剩余未知值得在初试验证，且无足以否定邀请的已知阻碍 | 最值得验证的案例、关键未知及为何可留到初试验证 |
| 暂不建议初试 `do_not_invite` | 明确岗位条件不匹配，或现有材料缺少足以优先安排的核心相关信号 | 分清“已知不匹配”与“材料信号不足”，引用位置、保留相反线索；后者不宣称能力已证伪 |
| 暂无法判断 `pending_evidence` | 关键材料不可读/缺失、归属无法确定，或关键岗位标准冲突，当前无法可靠作出简历判断 | 具体阻碍、最小补充和不受影响的已完成工作 |

默认给前两种判断；第三种是明确阻碍时的例外，不能因为个人贡献未核实、缺作品、七项未覆盖或培养节点未定就要求先交材料再决定。通常把这些问题带入初试；确实不足以支持邀请时直接说明暂不建议的材料依据。不设“验证性初试”等模糊的第四类，初试本身即验证。

不要求七项或所有核心都supported才初试；没有提及不等于gap。已知不匹配也不能被加分或业务成绩抵消。可以提出可选补充材料，但不将其变成默认前置作业，不因用户不补充就停下已有材料的判断。

## 批量优先级

批量筛选默认同时给推荐梯队，不等用户追问，也不以提供名额为开始条件：

- **优先初试 `first_batch`**：相对本批，核心相关线索更具体、本人责任更清楚，最值得先验证。
- **可安排初试 `consider`**：核心邀请依据已成立，但相对关键未知更多或迁移更间接；不是收纳所有“有一点相关经历”的人。
- **暂不优先 `not_priority`**：现有材料不足以优先安排或已有明确不匹配，对应暂不建议初试。
- **暂无法比较 `undetermined`**：对应暂无法判断；不能把材料障碍解释为能力最弱。

单人筛选不强行给相对梯队。用户要求精确顺序时，证据足够才排；同梯队难分就并列并说明局限。允许多数乃至全部建议初试，不设通过率、不为凑梯队强行淘汰。给出已提供容量下的先后建议，但不把容量截断以下的人改写为能力不合格。

比较依据来自同版岗位：先比较核心任务的具体相关性、本人判断与贡献的可辨程度，以及已明确其他必需的支持或阻碍；再解释可迁移性和未知。加分只在前述基础上区分，不用名校、大厂、行业年限、案例数量、标签数量、平均分或伪精确概率排序。梯队理由须说明与本批相邻梯队的实际差别，不仅重复“待核实”。

## 分层交付与后续接续

按 `assets/screening-summary.md` 先交付可读决策摘要：范围、同版岗位重点和批量主表。主表至少包含**候选人、初试建议、推荐梯队、体验/产品核心依据及位置、支持范围与初试成立理由、最大风险、初试首要验证点**。流程状态与身份备注另列。单人可用短段落，不强制大表。

摘要说明为何以产品能力为核心招聘，候选人侧主要体现哪类证据，必要业务知识与其他责任有何阻碍。不要只因行业或技术贴合推荐为产品专家，也不因跨行业否定产品能力；若岗位实际业务主导，说明模型适用边界。

详细记录保留：

1. 2–4条差异化理由与完整证据链，相关反证、贡献归属及核验边界。
2. 只集中展示真正影响建议的“要求及层级—最低表现—证据/未知—当前阶段影响”；其余简列，避免重复十几行相同“待核实”。
3. P1–P7完整观察状态和按需的最小验证问题；未展示的为未充分观察。独立业务、管理等要求单列，不与七项平均求和。
4. 最值得深挖的真实案例、具体未知，以及初试应优先安排的走查或追问。

摘要不堆满每人的七项与全量要求表；详细记录或附录可链接查看，不以精简为由丢掉证据。

输出默认维护一个最新入口 `筛选汇总.md`，同步保存推荐梯队及排序，入口内链接当前详细记录。修订前保留历史版，旧报告标明已被哪版替代，不能留下多个未标状态的“当前结论”。分别记录岗位版本、筛选判断版本、日期与材料范围；只改变决策范围、补充线索或排序，不虚增岗位版本。建议变化说明来自新证据、标准变化还是决策范围变化，保留旧结论，不能假称能力因追问而变化。发现误读材料或误用标准可更正，说明原错误、纠正依据和受影响结论，不为维持历史答案保留错误。
